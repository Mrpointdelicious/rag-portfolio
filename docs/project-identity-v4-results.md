# project 数据库授权适配 v4

日期：2026-10-12。结论：已依据 project 数据库文档和实际业务代码，实现 JWT 身份、机构角色、医患关系复核与合成贯穿验收。**真实患者生产接入仍为 NOT_READY，业务评测仍为 PARTIAL。**

## 本轮实际改变

固定登录夹具之外，新增可插拔的 project JWT 验证器与最小数据库读取层。服务端从数据库确定身份角色和机构，用近期未结束问诊确定医生对指定患者的访问关系。患者只访问自己，同机构但无有效关联的医生、管理员、停用/未审核账号均被拒绝。

统一当前 `project.dbuser.Id`，明确数据代次；旧库数字、OldId、同名、手机号均不自动转成当前身份。每次复核重新读只读元数据；持久授权指纹与会话代次阻止已观察到的撤销在恢复后复活。现有服务和生产入口未切换。

规则的详细证据、SQL 权限、运行方法和边界见 [MetaAgent 设计说明](../../metaAgent/docs/project-identity-v4.md)。数据库文档是分析依据，其中历史任务的部署指令未被当作本轮授权。

## 验收

最终数字和固定条件见 [公开结果](../artifacts/project-identity-v4/summary.json)，[交付隔离检查](../artifacts/project-identity-v4/delivery-audit.json) 包含实际 wheel/sdist 和 Docker 构建上下文检查。

- 固定 51 项条件，复查账号审核状态后追加冻结 5 项；包括登录伪造、身份歧义、跨机构、角色停用、关系结束/过期、撤销与恢复、数据库故障、进程重启和原生 Agent 贯穿。
- 最终通过 56/56 项；旧共享授权回归 41/41 项通过，完整测试 RAG 284 项、MetaAgent 404 项通过。
- 测试数据库仅有 7 张真实 CREATE TABLE 和自建记录；实际运行的授权账号无法更新患者表，也无法读取 Password。
- .NET 控制器来自当前后端实际源码，Service/Repository 使用合成夹具。原生记录任务零模型调用。未接入现有患者数据库或真实登录服务。
- 旧 v3 的 41 项跨进程授权/清理验收和两个项目完整测试另外回归。原有失败尝试全部保留，不以最后一次结果覆盖。

首次建表失败来自旧 COMPACT 表结构在 MySQL 8 的严格 DDL 检查；仅调整自有建表会话的兼容设置，未修改生产库或表字段。初次 51 项通过后，账号审核代码复查促使规则收紧为 Status=1；最终结果以包含追加条件的验收为准。

交付审计曾因本轮冻结脚本的格式化未列入允许修改范围，以及混用了规范化内容指纹和文件字节指纹而失败。已修正检查口径，重新计算语料/索引内容指纹确认与原基线一致；未改写语料、索引或历史评测结果。所有失败审计记录保留。

## 对真实患者生产接入的评价

身份链已从固定测试账号推进到与实际 JWT/表结构一致的适配，并验证动态关系撤销。但现在仍是受控隔离工程验证，尚不能把生产服务指向真实患者后宣称可用。

下一步应先完成**实际后端的逐路由授权和逐查询机构/记录归属约束**，同时设计数据库内持久授权版本及登录会话撤销。当前数据库没有显式医患授权表，7 天未结束问诊是本轮选择的保守临时规则，持续随访须有明确的授权生命周期。两次检查之间撤销又恢复为完全相同值的情况，目前无法靠快照发现。

还需核验运行系统究竟使用双库还是合并 project，以及迁移报告与患者的真实来源关联。现有文档记录过来源不一致，当前后端又仍有姓名桥接；这部分不能用合成夹具的成功替代。

后续生产门槛还包括受管签名密钥与 TLS、实际 .NET 宿主和依赖告警修复、容量/并发验证以及独立临床审核。默认入口保持原状，本轮没有生产部署。
